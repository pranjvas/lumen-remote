# Build notes: agent

Role "agent": the on-TV Lumen Agent 0.2.0 (Tizen web app), its build/sign and install scripts, and the server adapter that receives it.

## Files

| File | What it is |
|---|---|

## Exports and signatures

`server/adapters/agent.js`

```js
export function createAgent({ config, data, log, store, lan, rest })
// → { start(), stop(): Promise<void>, setDemand() {}, launch(): Promise<{ value }>, request(type, args?): Promise<{ value }>, getIcon(appId): Promise<{ type: 'image/png', buffer } | null> }
```

- `start()` (idempotent): `lan.route('/agent', { upgrade })`, publishes `conn.agent: 'unknown'` and `conn.agentNote: null`, and switches to `'offline'` after a 35 s grace if no agent connects (longer than the agent's 30 s max backoff, so a running agent reconnecting after a server restart does not flash "offline").
- `stop()` (idempotent): unregisters the route, rejects pending requests, closes the agent socket with 1001, closes the `WebSocketServer`.
- `request(type, args)`: `type` ∈ `apps | icon | exit` (else `LumenError('INVALID')`); `UNAVAILABLE` when no agent is connected; sends `{ ...args, t:'req', rid, type }` (rid = UUID); resolves `{ value: data }`; rejects `FAILED` on `ok:false` or after 8 s.
- `launch()`: `{ value: 'online' }` without relaunching when already online; `TV_OFF` when `conn.tv` is `standby`/`off`; otherwise `conn.agent: 'launching'`, `rest.launch(config.agent.appId)`, resolves `{ value: 'launching' }`. A REST failure → `LumenError('FAILED', 'Open "Lumen Agent" from the TV Apps screen')` (spec §9.1) and `offline`. No hello within 20 s → `offline` plus a `conn.agentNote` suggesting a rebuild.
- `getIcon(appId)`: rejects ids outside `/^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$/` (no path separators), then memory → `data/icons/<id>.png` → agent `icon` request (user priority on the icon queue). Failed icons are not re-requested for 10 min.

## Protocol as implemented (spec §5.5)

Agent → PC:
- `{ t:'hello', agent:'0.2.0', pcHost, snapshot }` (`agent` = `agent-config.json` `version`, falling back to the app's own version).
- `{ t:'state', snapshot }` every 5 s, and within ~1 s of a change in the cheap synchronous fields (source, channel, volume, mute, output codec, caption are re-read every second; systeminfo is read with each 5 s state).
- `{ t:'event', kind:'volume', value }` from `tvaudiocontrol.setVolumeChangeListener`.
- `{ t:'reply', rid, ok, data | error }`.

Snapshot: `source {type, number}` (tvwindow.getSource), `connected` / `disconnected` `[{type, number}]` (systeminfo VIDEOSOURCE), `channel {name, number, type} | null` (null unless source type is `TV`; name/number from tvchannel, `type` from hybridchannelinfo `channelType`, number is a string such as `"1927"` or `"7-1"`), `audio {volume, mute, outputCodec}`, `caption 'on'|'off'|null` (`tizen.tvinfo.getCaptionValue('CAPTION_ONOFF_KEY')` normalised), `build` (BUILD.buildVersion), `panel {w, h}` (PANEL), `system {cpuLoad, memAvailable, memTotal, storageFree, storageTotal}` (CPU.load, getAvailableMemory/getTotalMemory, sum of INTERNAL STORAGE units). Every TV call is wrapped; a missing API yields `null` for that field only.

PC → agent: `{ t:'req', rid, type:'apps' }` → `[ {id, name, show:true, iconPath} ]` (getAppsInfo, `show` only, minus our own app id and package); `{ type:'icon', appId }` (a Tizen id) → PNG data URL (`<img>` of `file://<iconPath>` → canvas, scaled to ≤ 256 px; if that fails or the canvas is tainted, XHR the file into a blob URL and rasterise that); `{ type:'exit' }` → reply, then `application.exit()`.

Agent behaviour: card painted, `hide()` after 400 ms (and again whenever it becomes visible, e.g. relaunched by the PC or opened from Apps, which also retries the connection immediately); `ws://pcHost:pcPort/agent?key=…` with 2/5/10/30 s backoff and a 10 s connect timeout; exits after 30 min without a PC link; a bad or missing `agent-config.json` keeps the card visible with the error for 10 s, then exits. It never calls a TV setter.

## Store mapping (spec §8.3, §9.5)

Live readings use `{ src:'agent', via:'agent:<field>', ttlMs: 15000 }`:
`input.source` (also written by ipcontrol; the store's ranking rule keeps fresh live values), `input.connected`, `input.available` (connected + disconnected, sorted TV, HDMIn, AVn, COMPONENTn, others), `channel.current`, `audio.volume` (`via` `agent:audio.volume`, or `agent:event` for listener events; 0–100 only), `audio.mute`, `audio.outputCodec`, `caption.state`, `system.cpuLoad` (0–1), `system.memAvailable`, `system.memTotal`, `system.storageFree`, `system.storageTotal` (bytes).

No TTL: `device.firmware` (build string), `device.panel` (`"3840x2160"`), `app.installed` (`via:'agent:apps'`).

`conn.agent` and `conn.agentNote` use `src:'derived'` (not persisted to the state cache).

## Interpretations and deviations

1. **app.installed ids are REST launch ids.** The agent sees Tizen ids (`org.tizen.netflix-app`), but REST launches store ids (`3201907018807`) or `<10-char package>.<name>` ids and 404s `org.tizen.*` / `com.samsung.*` (research, area-power-apps-inputs). The adapter maps 11 Tizen ids to their store ids. I matched them by name and version between the probe's `getAppsInfo` output (`data/probe/ui-probe.json`) and the REST table: Netflix, YouTube, Prime Video, Apple TV, Internet, Apple Music, Spotify, Plex, SmartThings, Gallery and Alexa. It keeps only REST-launchable ids, drops background services (ids ending in `service`) and duplicates, merges `name/color/short` from `catalog/apps.js`, and sorts curated apps first (catalogue order), then the rest by name. On the probe data, 224 visible apps become 21 launchable ones. Items are `{ id, name, color, short, icon }`, with `color`/`short`/`icon` set to `null` when unknown or not fetched yet. Icons are fetched by Tizen id but cached and served under the launch id (`/api/icon/<launchId>`). **Suggestion for tv-adapters:** move the pairs into `catalog/apps.js` as a `tizenId` field. The table lives in the adapter for now because I don't own the catalogue.
2. **Icons are prefetched.** After the app list arrives, icons for apps with an `iconPath` are fetched one at a time in the background (`poll` priority). `app.installed` is republished at most once a second as icons arrive. A browser request for `/api/icon/…` jumps the queue (`user` priority).
3. **Expected agent version** = `config.agent.version` if set, otherwise the `version` attribute in `companion/agent/config.xml`, which build.ps1 also stamps into `agent-config.json`. That gives one source of truth.
4. **conn.agentNote** = `"Rebuild the TV agent: it runs X, this server expects Y; it was built for A, this PC is now B"` (the parts that apply), or `null`. After a launch timeout it is "The TV agent did not connect within 20 s. If this PC's network address changed, rebuild the TV agent."
5. **Liveness:** any message resets a 15 s timer. When it expires, `offline` is published and the socket is terminated so a live-but-stuck agent reconnects. A socket close publishes `offline` at once, except while `launching`. A newer connection replaces the old one (close code 4000).
6. **Key:** `config.secrets.agentKey` (set by core `loadConfig`), falling back to `data.readJson('secrets.json').agentKey`. The comparison is `timingSafeEqual` over SHA-256 digests, so length leaks nothing. Rejected upgrades are destroyed and logged by path only, never the query.
7. The snapshot omits `foreground` (the spec says leave it null; REST owns `app.foreground`) and adds `disconnected` (the brief asks for it; it feeds `input.available`).
8. **build.ps1 extras:** parameters `-TvHost`, `-PcPort`, `-SigningProfile` (default `Q95T`; `$Profile` is a reserved PowerShell variable), `-TizenCli`. TV host and LAN port default to `data/config.json` `tv.host` / `lan.port` when present. It uses absolute paths for `-out` / `--`, excludes `agent-config.example.json` from the package, and checks that the WGT contains config.xml, index.html, agent.js, agent-config.json and both signatures. Secrets JSON is written UTF-8 without BOM (tmp + rename). It prints the address, port, version, path and size, never the key.
9. **install.sh extras:** it exits 2 if another `sdb -s` client is running (`LUMEN_SDB_FORCE=1` skips that check) and runs `sdb connect` when the TV is not listed. It reports success only when the output contains `app_id[lumenrmt01.LumenAgent] install completed` and `vd_applist` shows the config.xml version. `LUMEN_TV` overrides `192.168.1.2:26101`.

## Known gaps / for the orchestrator

- **`.gitignore` (not my file) must gain `companion/agent/agent-config.json` (contains the agent key) and `companion/build/`.** Neither is ignored today. `data/` already is.
- Nothing here ran on the real TV (not allowed). Still unverified on the Q95T:
  - the CSP in config.xml;
  - loading another app's `file://` icon into a canvas (the blob fallback covers a tainted canvas but not a blocked read);
  - the exact `getCaptionValue('CAPTION_ONOFF_KEY')` return values (handled: `CAPTION_ON`/`CAPTION_OFF`, `ON`/`OFF`, booleans, 1/0);
  - how long a hidden agent keeps running;
  - the 0.1.0 → 0.2.0 upgrade dropping the `lumenrmt01.LumenService` service app.
- The baked `pcPort` comes from build time (8791, or `data/config.json` `lan.port`). If the server's LAN port or the PC address changes, rebuild. The adapter flags an address change in `conn.agentNote` only if the agent can still reach the server. Otherwise the 20 s launch timeout note covers it.
- The Tizen→store id table only covers apps verified on this TV. Other `org.tizen.*` / `com.samsung.*` apps are hidden from `app.installed` because REST cannot launch them.
- Interaction with core: `app.installed` from the agent is persisted to the state cache (`src:'agent'`). At startup, core seeds the curated list with `src:'derived'`, which replaces the cached copy until the agent says hello again.
- Running build.ps1 during verification created `data/secrets.json` (it did not exist). It now holds all four 32-byte hex secrets, and core's `ensureSecrets` keeps them.
